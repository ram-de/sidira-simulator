## Q1 — Control-arm artifact

**Question:** When the LLM reacts in the control arm (no proposed change), what does it see?

### Options

**A. Status-quo prose doc, hand-authored per capability.** A separate `current_state_prd` field lives next to `Capability.reverse_prd`; PMs write the "how it works today" framing manually per simulation.
- ✅ Maximum control over the framing.
- ❌ Doubles authoring burden per capability. Every new capability needs two docs. PMs will copy-paste-modify, which means they'll diverge.

**B. Reuse `Capability.reverse_prd`; skip the proposed-change appendix.** The Feature Pack already carries a reverse-engineered current-state PRD. Control-arm prompt composer drops the `## The proposed change` section + opener-hook reference and reacts to the product-as-is. *(RECOMMENDED.)*
- ✅ Zero new authoring. The current-state description we need is already in the Feature Pack.
- ✅ Guarantees treatment and control see IDENTICAL product context — the only diff is the presence/absence of the proposed-change section. Apples-to-apples.
- ❌ The reverse_prd was written for treatment-arm framing ("here is your current product, REACT to this change"); using it as a standalone might land slightly flat. Mitigation: tweak the control-arm prompt's opener instruction to ask "how does this product work for you today, what works/what doesn't" instead of "react to this change".

**C. No artifact, no proposed-change section.** Strip the proposed-change paragraph from the existing prompt; the agent just reacts to the persona prompt + capability context.
- ✅ Smallest possible change.
- ❌ The current prompt's `## Your task` section pivots HARD on the proposed change ("React to this proposed change as **you**…"). Without that pivot the agent has nothing concrete to react to. The opener instruction from #77 also assumes there's a change to anchor on. Likely produces low-signal reactions.

### Recommendation: **B**

The Feature Pack `Capability.reverse_prd` IS the current-state product description. Adding a separate field is duplication that drifts. The implementation is a variant of `compose_identity_prompt` that:
- Keeps `## Who you are`, `## About you specifically`, `## Behavioral snapshot`, `## The product today` (with `reverse_prd` + `reverse_figma_summary`).
- Drops `## The proposed change` and the proposed-PRD section.
- Replaces `## Your task` with a status-quo framing: "React to the product as it works for you TODAY. What works? What frustrates you? What would you want changed?"
- KEEPS the `### How to open` instructions from #77 — they're identity-grounded, not change-anchored. Tighten the wording to "open from `current_state` or `recent_gripe`" since "specific number/item from the proposed change" no longer applies.

**Codex regression risk:** any change to `prompt_composer.py` touches the file that took the #77 templated-opener fix. The `/plan-eng-review` on #89 should explicitly check that both arms still emit identity-grounded openers, not polite-hedge templates. The same negative-template list (`"Honestly, I'm not"`, `"As someone who"`, `"mixed feelings"`, etc.) must stay applied to both arms.

## Q3 — Paired vs independent sampling

**Question:** Does a treatment agent and its control counterpart share the SAME identity_seed, or do they get fresh draws?

### Options

**Paired.** Same `(persona_id, sample_index, run_seed)` → same `identity_seed` in both arms. "Maya in the treatment arm" and "Maya in the control arm" are the same hypothetical Maya seeing two different product states. *(RECOMMENDED.)*

**Independent.** Fresh `(sample_index)` for each arm. Treatment and control are two different draws from the persona distribution.

### Why paired wins

1. **Statistical power.** Per-agent delta (`sentiment(treatment) − sentiment(control)`) cancels the persona-specific variance. CI shrinks. We get usable signal at N=20-30 per persona instead of needing N=60-100 for independent samples.

2. **Conceptual model matches.** A simulation is not a real A/B test with different users. It's the same hypothetical user observing one of two product states. The natural PM question is "what would Maya say WITH the change vs WITHOUT it" — not "two random Maya-shaped users in two parallel universes." Paired is what the PM is mentally modeling.

3. **Cheaper.** Paired bootstrap is robust at smaller N. Lower-population sims become useful, which matters since the simulator's LLM cost scales linearly with N.

4. **Trivial to implement.** `services/identity_seed.py:draw_identity_seed(persona, sample_index, run_seed)` is already deterministic. Paired sampling literally means "call it with the same args twice" — once for the treatment cohort, once for the control. The implementation is zero new code; it's a flag on the orchestrator.

### Why someone would argue for independent

- "It matches real A/B more closely." True, but the simulator isn't a real A/B test — it's a thought experiment. Modeling it as a real A/B test imports the variance without importing the user-base size that real A/B has.
- "Same identity might over-correlate the two arms." Slightly, but that's exactly the property the paired analysis EXPLOITS to get tighter CIs. Not a bug.

### Recommendation: **Paired**

Lock paired. Independent stays in the carryover-followups list for a future "real A/B harness" feature if Phase 9 ever needs it for calibration ground-truth comparisons.

## Q4 — Cost model

**Question:** A 50-population sim becomes 100 agents in A/B mode (2× LLM cost + latency). How is this surfaced to the PM, and what safeguards exist?

This question has two layers — pricing (customer-facing) and engineering (safety nets).

### Pricing (defer to Phase 7)

There's no customer yet. Lumen (Phase 7 #40) is the first. Setting per-customer pricing today is premature — we don't know what the LLM cost actually is in steady state (which depends on the score-formula choice in Q2 and the prompt token count from Q1).

**Recommendation: ship without a pricing decision.** Phase 7 onboarding includes a "this run costs ~$X in LLM" line item; A/B mode shows 2× that. Real pricing waits until we know the unit economics.

### Engineering safeguards (lock now)

Three pieces:

**(a) Wizard cost preview.** Before the PM submits an A/B run, show:
- `≈ N treatment agents + M control agents = (N+M) total LLM calls`
- `Estimated cost: ~$X` (computed from a per-agent token estimate × current Groq/Anthropic price). If we don't have a reliable per-agent estimate yet, show the call count only — better honest "X calls, ~Y cents each" than a fake-precise total.

**(b) Hard cap per arm.** `treatment_agents ≤ 200, control_agents ≤ 200`. Today's `MAX_AGENTS` is 50 per sim; A/B mode would otherwise let `population_size=10000 × treatment_fraction=0.5 = 5000-per-arm` blow through that. The cap is a safety net against a runaway wizard, not a statistical claim. Documented at the schema validation layer.

**(c) Both-arms confirmation step.** If `total_agents > 100`, the wizard shows a "this is a large run, $X estimated" intermediate confirm before submit. Same shape as the existing `population_size > MAX_AGENTS` warning we surface today.

### Recommendation: **Wizard preview + per-arm cap of 200 + confirm-if-large**

Pricing waits for Phase 7. The two safety nets matter today.
