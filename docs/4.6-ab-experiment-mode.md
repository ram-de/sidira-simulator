## Q1 — Control-arm artifact

**Question:** When the LLM reacts in the control arm (no proposed change), what does it see?

### Options

**A. Status-quo prose doc, hand-authored per capability.** A separate `current_state_prd` field lives next to `Capability.reverse_prd`; PMs write the "how it works today" framing manually per simulation.
- ✅ Maximum control over the framing.
- ❌ Doubles authoring burden per capability. Every new capability needs two docs. PMs will copy-paste-modify, which means they'll diverge.

**B. Reuse `Capability.reverse_prd`; skip the proposed-change appendix.** The Feature Pack already carries a reverse-engineered current-state PRD. Control-arm prompt composer drops the `## The proposed change` section + opener-hook reference and reacts to the product-as-is. *(RECOMMENDED.)*
- ✅ Zero new authoring. The current-state description we need is already in the Feature Pack.
- ✅ Guarantees treatment and control see IDENTICAL product context — the only diff is the presence/absence of the proposed-change section. Apples-to-apples.
- ❌ The reverse_prd was written for treatment-arm framing ("here is your current product, REACT to this change"); using it as a standalone might land slightly flat. Mitigation: tweak the control-arm prompt's opener instruction to ask "how does this product work for you today, what works/what doesn't" instead of "react to this change".

**C. No artifact, no proposed-change section.** Strip the proposed-change paragraph from the existing prompt; the agent just reacts to the persona prompt + capability context.
- ✅ Smallest possible change.
- ❌ The current prompt's `## Your task` section pivots HARD on the proposed change ("React to this proposed change as **you**…"). Without that pivot the agent has nothing concrete to react to. The opener instruction from #77 also assumes there's a change to anchor on. Likely produces low-signal reactions.

### Recommendation: **B**

The Feature Pack `Capability.reverse_prd` IS the current-state product description. Adding a separate field is duplication that drifts. The implementation is a variant of `compose_identity_prompt` that:
- Keeps `## Who you are`, `## About you specifically`, `## Behavioral snapshot`, `## The product today` (with `reverse_prd` + `reverse_figma_summary`).
- Drops `## The proposed change` and the proposed-PRD section.
- Replaces `## Your task` with a status-quo framing: "React to the product as it works for you TODAY. What works? What frustrates you? What would you want changed?"
- KEEPS the `### How to open` instructions from #77 — they're identity-grounded, not change-anchored. Tighten the wording to "open from `current_state` or `recent_gripe`" since "specific number/item from the proposed change" no longer applies.

**Codex regression risk:** any change to `prompt_composer.py` touches the file that took the #77 templated-opener fix. The `/plan-eng-review` on #89 should explicitly check that both arms still emit identity-grounded openers, not polite-hedge templates. The same negative-template list (`"Honestly, I'm not"`, `"As someone who"`, `"mixed feelings"`, etc.) must stay applied to both arms.

## Q3 — Paired vs independent sampling

**Question:** Does a treatment agent and its control counterpart share the SAME identity_seed, or do they get fresh draws?

### Options

**Paired.** Same `(persona_id, sample_index, run_seed)` → same `identity_seed` in both arms. "Maya in the treatment arm" and "Maya in the control arm" are the same hypothetical Maya seeing two different product states. *(RECOMMENDED.)*

**Independent.** Fresh `(sample_index)` for each arm. Treatment and control are two different draws from the persona distribution.

### Why paired wins

1. **Statistical power.** Per-agent delta (`sentiment(treatment) − sentiment(control)`) cancels the persona-specific variance. CI shrinks. We get usable signal at N=20-30 per persona instead of needing N=60-100 for independent samples.

2. **Conceptual model matches.** A simulation is not a real A/B test with different users. It's the same hypothetical user observing one of two product states. The natural PM question is "what would Maya say WITH the change vs WITHOUT it" — not "two random Maya-shaped users in two parallel universes." Paired is what the PM is mentally modeling.

3. **Cheaper.** Paired bootstrap is robust at smaller N. Lower-population sims become useful, which matters since the simulator's LLM cost scales linearly with N.

4. **Trivial to implement.** `services/identity_seed.py:draw_identity_seed(persona, sample_index, run_seed)` is already deterministic. Paired sampling literally means "call it with the same args twice" — once for the treatment cohort, once for the control. The implementation is zero new code; it's a flag on the orchestrator.

### Why someone would argue for independent

- "It matches real A/B more closely." True, but the simulator isn't a real A/B test — it's a thought experiment. Modeling it as a real A/B test imports the variance without importing the user-base size that real A/B has.
- "Same identity might over-correlate the two arms." Slightly, but that's exactly the property the paired analysis EXPLOITS to get tighter CIs. Not a bug.

### Recommendation: **Paired**

Lock paired. Independent stays in the carryover-followups list for a future "real A/B harness" feature if Phase 9 ever needs it for calibration ground-truth comparisons.

## Q4 — Cost model

**Question:** A 50-population sim becomes 100 agents in A/B mode (2× LLM cost + latency). How is this surfaced to the PM, and what safeguards exist?

This question has two layers — pricing (customer-facing) and engineering (safety nets).

### Pricing (defer to Phase 7)

There's no customer yet. Lumen (Phase 7 #40) is the first. Setting per-customer pricing today is premature — we don't know what the LLM cost actually is in steady state (which depends on the score-formula choice in Q2 and the prompt token count from Q1).

**Recommendation: ship without a pricing decision.** Phase 7 onboarding includes a "this run costs ~$X in LLM" line item; A/B mode shows 2× that. Real pricing waits until we know the unit economics.

### Engineering safeguards (lock now)

Three pieces:

**(a) Wizard cost preview.** Before the PM submits an A/B run, show:
- `≈ N treatment agents + M control agents = (N+M) total LLM calls`
- `Estimated cost: ~$X` (computed from a per-agent token estimate × current Groq/Anthropic price). If we don't have a reliable per-agent estimate yet, show the call count only — better honest "X calls, ~Y cents each" than a fake-precise total.

**(b) Hard cap per arm.** `treatment_agents ≤ 200, control_agents ≤ 200`. Today's `MAX_AGENTS` is 50 per sim; A/B mode would otherwise let `population_size=10000 × treatment_fraction=0.5 = 5000-per-arm` blow through that. The cap is a safety net against a runaway wizard, not a statistical claim. Documented at the schema validation layer.

**(c) Both-arms confirmation step.** If `total_agents > 100`, the wizard shows a "this is a large run, $X estimated" intermediate confirm before submit. Same shape as the existing `population_size > MAX_AGENTS` warning we surface today.

### Recommendation: **Wizard preview + per-arm cap of 200 + confirm-if-large**

Pricing waits for Phase 7. The two safety nets matter today.

## Q2 — Score formula (eng review)

**Question:** Given Q3=paired, what's the statistical method that turns per-agent sentiment deltas into a lift number + CI the PM can act on?

### Options considered

**A. Paired bootstrap on per-agent sentiment delta.** Non-parametric. For each of K bootstrap resamples, draw N pairs with replacement, compute mean delta. Take 2.5/97.5 percentiles as the 95% CI. *(RECOMMENDED.)*

**B. Welch's t-test on per-agent paired delta.** Parametric. Assumes the delta distribution is roughly normal. With sentiment values in {0.0, 0.5, 1.0} weighted by confidence, the deltas are bounded and discrete-ish; normality is a stretch at small N.

**C. Wilcoxon signed-rank / sign test.** Non-parametric. Gives a p-value but NO confidence interval on the magnitude of the lift — only "is it different from zero." PMs need the magnitude.

**D. Bayesian credible interval on lift proportion.** Most interpretable for product decisions, but needs prior selection + posterior computation infra we don't have today. Premature.

### Why A wins

1. **CI shape matches the existing per-arm confidence_score CI.** `services/scoring.py:ScoringService._compute_score` is already wrapped in a bootstrap to produce `SimulationResult.confidence_score_ci`. Same `bootstrap_resamples` knob from `ScoringConfig`. Implementation is two paths through the same machine.

2. **Non-parametric.** No normality assumption. Sentiment values come from `_SENTIMENT_VALUE = {positive: 1.0, neutral: 0.5, negative: 0.0}` weighted by `sentiment.confidence` — bounded, discrete, and small-N. Bootstrap handles all of that.

3. **PM-readable output.** Bootstrap returns a CI directly. "Lift is +12 with 95% CI [+3, +21]" is the line the PM needs. Sign test gives p-value (less actionable); t-test assumes normality (suspicious); Bayesian needs prior justification (overengineered for v1).

4. **Reproducible.** Seed the RNG with `run_seed`. Same data + same seed → same CI. Mirrors how `_bootstrap_score_ci` already works.

### What the lift quantity actually is

Two layers — be explicit so #90 / #91 implementation doesn't drift:

**Internal (per-agent delta) — drives the bootstrap:**
```python
def _agent_delta(treatment: AgentAnalysis, control: AgentAnalysis) -> float:
    """Confidence-weighted sentiment delta for one matched pair."""
    t_value = _SENTIMENT_VALUE[treatment.sentiment.sentiment]
    c_value = _SENTIMENT_VALUE[control.sentiment.sentiment]
    # Confidence applied to both, so an unconfident +1 - unconfident -1
    # carries less weight than a confident pair with the same sentiments.
    t_weighted = treatment.sentiment.confidence * t_value
    c_weighted = control.sentiment.confidence * c_value
    return t_weighted - c_weighted
# Range: [-1.0, +1.0]
```

**Display (PM-facing) — derived, surfaced on `SimulationResult`:**
```
lift = treatment.confidence_score - control.confidence_score  # range [-100, +100]
lift_ci = (low, high)                                          # in confidence_score units
```

Bootstrap operates on per-agent deltas. The CI on `lift` is derived by scaling the per-agent-delta CI from [-1, +1] into [-100, +100] — same scale-factor used by `_compute_score` (sentiment_score × `sentiment_weight × 100` etc., already proven by `test_aggregate_parity_snapshot`). The CI percentile boundaries hold under this linear scaling.

### Pairing mechanics

Per Q3 (locked = paired), pairing is by `(persona_id, sample_index)`. Implementation:

```python
def _match_paired_analyses(
    treatment_analyses: list[AgentAnalysis],
    control_analyses: list[AgentAnalysis],
) -> tuple[list[tuple[AgentAnalysis, AgentAnalysis]], int, int, int]:
    """Match treatment and control agents by (persona_id, sample_index).

    Returns:
      paired_pairs: list of (treatment, control) tuples, both sentiment-classified successfully.
      unpaired_treatment: count of treatment agents with no matching control.
      unpaired_control: count of control agents with no matching treatment.
      dropped_for_sentiment_failure: count of pairs dropped because one or both
        agents had sentiment_failed=True (the LLM classification fell back to
        the neutral default; including that pair in the bootstrap would
        introduce phantom signal).
    """
```

Three unhappy paths to surface explicitly (NOT silently swallow):

- **Unmatched treatment agent** (control arm failed for this `(persona_id, sample_index)`): dropped from lift. Counter surfaced.
- **Unmatched control agent** (treatment arm failed): dropped from lift. Counter surfaced.
- **`sentiment_failed=True` in either arm**: dropped from lift. Counter surfaced. Including a failed sentiment classification (which defaults to neutral) would create phantom signal in the paired bootstrap.

### `SimulationResult` extensions for A/B mode

```python
class SimulationResult(BaseModel):
    # ... existing fields preserved ...

    # A/B mode fields — all None for single-arm sims (backwards compatible).
    treatment_score: float | None = None      # per-arm confidence_score
    control_score: float | None = None        # per-arm confidence_score
    lift: float | None = None                  # treatment_score - control_score, [-100, +100]
    lift_ci: tuple[float, float] | None = None # 95% paired-bootstrap CI on lift
    lift_paired_n: int | None = None           # matched-pair count used in bootstrap
    lift_unpaired_treatment: int = 0           # treatment agents dropped (no matching control)
    lift_unpaired_control: int = 0             # control agents dropped (no matching treatment)
    lift_sentiment_failure_drops: int = 0      # pairs dropped because sentiment classification failed
```

### Degenerate-case behaviour (must be explicit, not silent)

| Case | Behaviour |
|---|---|
| All matched pairs (happy path) | Bootstrap runs; `lift` + `lift_ci` populated; unpaired counters = 0 |
| Some pairs dropped (partial-failure) | Bootstrap runs on remaining pairs; counters surface what was dropped; `lift_ci` reflects only the matched subset |
| `lift_paired_n == 0` (no usable pairs) | `lift = None, lift_ci = None`. Per-arm `confidence_score` still computed independently so the result-table per-arm rows still render. Frontend shows "lift not computable — too many agent failures" with the per-arm scores intact. |
| `lift_paired_n == 1` (single matched pair, today's pre-weighted-population reality) | `lift = single_delta`, `lift_ci = (lift, lift)` (degenerate; bootstrap of N=1 always returns the same value). Frontend banner: "CI not meaningful at N=1." NOT a failure — common case until #6 (weighted population) is deployed. |
| Bootstrap resamples = 0 (`ScoringConfig.bootstrap_resamples=0`) | `lift` populated, `lift_ci = None`. Matches the existing per-arm behaviour when CI is skipped. |
| Zero variance across all pairs (all deltas identical) | Bootstrap returns the same value every resample; `lift_ci = (lift, lift)`. Tight-but-correct. |

### Statistical config (reuse, don't fork)

| Setting | Source | Value |
|---|---|---|
| `bootstrap_resamples` | `ScoringConfig.bootstrap_resamples` (existing) | 1000 (current default) |
| CI level | hardcoded 95% (matches existing) | 2.5 / 97.5 percentile |
| RNG seed | `run_seed` passed through (existing pattern) | reproducible |

No new config fields. The paired-bootstrap path inherits everything.

### Test fixtures (`test_statistics.py` shape)

Six known-answer cases pin the formula:

1. **Zero-lift, balanced pairs.** Per-agent deltas = 0 for all pairs. Expect `lift ≈ 0`, CI tight around zero.
2. **Positive lift, all pairs positive.** All deltas = +0.5. Expect `lift = 0.5 × 100 × sentiment_weight ≈ +30`; CI does not cross zero.
3. **Negative lift, all pairs negative.** Symmetric. CI does not cross zero on the negative side.
4. **Mixed lift, CI crosses zero.** Half pairs +0.3, half −0.3. Expect mean ≈ 0; CI crosses zero.
5. **Single matched pair (N=1 degenerate).** `lift_paired_n=1`, `lift_ci=(lift, lift)`.
6. **Partial-failure case.** 5 treatment + 3 control matched + 2 unmatched on each side. `lift_paired_n=3`, `lift_unpaired_treatment=2`, `lift_unpaired_control=2`, lift computed on the 3 matched pairs.

Plus the existing `test_aggregate_parity_snapshot` shape: a synthetic-known-answer fixture pinning that scaling per-agent delta CI by 100 produces the same magnitude CI as scaling the score itself by 100. Catches regressions in the [-1,+1] → [-100,+100] linear scaling.
