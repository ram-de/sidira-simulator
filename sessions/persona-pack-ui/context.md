# Session: persona-pack-ui — surface persona-pack v1.1 richness in the frontend

## Goal
Close the PM-facing gap on the personas side of the UI: the producer ships Persona Pack
v1.1 and the simulator renders it into agent prompts (chain proven end-to-end, #247/#248),
but the **frontend is still v1.0-shaped** — centroids, individual-row variety, alternative
weight schemes, and stability/honesty fields are all stored/rendered-into-prompts but shown
on **no page**. Make the v1.1 investment visible, read-only ("records on paper", DESIGN.md).
Then, separately, realign the stale Phase-4.5 build-pipeline tickets to today's architecture.

## Design Principles (read before building)
- **Data connectors are PLUGGABLE — Snowflake is ONE of N, never the only one.** Eventually
  CSV upload, BigQuery, Postgres, Redshift, etc. The backend scaffolding already anticipates
  this: the Protocol lives at `adapters/feature_stores/` and endpoints are generically named
  (`/feature-stores/{id}/test|preview`), NOT `/snowflake/...`. **Preserve that.** The UI must
  expose a **connector picker** (Snowflake = first option, others "coming soon"), never hardcode
  a Snowflake form. Any new endpoint/type/label stays connector-agnostic; Snowflake-specifics
  live behind the adapter boundary only.
- **Read-only, honest surfaces.** Persona packs are GENERATED by the clustering pipeline, never
  hand-authored (DESIGN.md §7.6). New surfaces are records, not glass — no edit affordances.
- **Read DESIGN.md before any UI/CSS/SVG change** (CLAUDE.md hard rule). 855 lines; relevant:
  §7.6 records-on-paper, refuse list §10, locked component specs.
- **Worktree for implementation** (CLAUDE.md hard rule): EnterWorktree before any code branch.
